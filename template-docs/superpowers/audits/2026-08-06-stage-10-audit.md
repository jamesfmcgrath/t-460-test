Date: 2026-08-06

Scope: audit the partially implemented Stage 10 work against the full stage
specification, close every gap, and prove the result with tests including a

## Summary

The implementation found on the branch was specification-conformant. It used a
single `LINT_PATHS` list as specified, not a parallel `THEME_*` copy of every
Makefile target, so nothing had to be reworked. One item was a genuine gap
(`make component` did not pre-fill the generator answers) and one consistency
defect was found during testing (`make spell` missing a flag CI already used).
Both are fixed.

`make check` still does not pass end to end on a theme project. Neither cause
was introduced by Stage 10, but Stage 10 makes both reachable for the first
time on a project whose only custom code is a theme.

## Fixes made

1. **`make component` pre-fills the generator answers.** The previous session
   left this open because drush's `--answer` ordering for the SDC generator
   could not be confirmed from published documentation. It was confirmed live
   against drush in the container:

   1. Theme machine name
   2. Component name
   3. Component machine name (defaults from the component name)
   4. Component description (optional)
   5. Library dependencies (optional)
   6. Need CSS?
   7. Need JS?
   8. Need component props?, then the prop wizard
   9. Need slots?, then the slot wizard

   The target now passes the first three via `--answer`, title-casing `NAME`
   for the label the same way `init.sh` does, and leaves the component shape
   questions interactive. Those are per-component design decisions and should
   not be guessed by a Makefile.

2. **`make spell` gained `--no-must-find-files`**, matching
   `.github/workflows/ci.yml` and the `spell` script in `package.json`.
   Splitting one lint path into two doubles the chance that a path contains
   only files cspell ignores, which would fail a run that ought to skip.

## Open items

1. **`make stan` spurious exit 1.** Narrowed, not fixed. Measured inside the
   container, phpstan writes exit code 0 to a file, so the analysis itself
   succeeds. `ddev exec vendor/bin/phpstan analyse <path>` still reports exit 1
   to the host whenever phpstan's output streams back out of the container, and
   returns 0 only when that output is redirected inside the container. Adding
   `--no-progress` does not change it, and neither does a shell wrapper, so the
   earlier note in PROJECT.md that a shell wrapper worked was too optimistic and
   has been corrected. Related: phpstan.neon includes phpstan-drupal's neon
   files explicitly while phpstan/extension-installer, pre-authorised by
   setup.sh since Stage 5, registers them too, producing the "included multiple
   times" warning. Dropping the explicit includes block was tried and rejected
   because it breaks the `parameters.drupal` schema.

2. **`make spell` on a fresh subtheme.** cspell reports 21 issues that are
   ordinary subtheme vocabulary (`favicons`, `msapplication`, `mstile`,
   `xlink`, `evenodd`, `linecap`, `miterlimit`, `focusable`, `ckeditor`,
   `subtheme`, `colour`, `colours`) plus names carried in the shipped
   `logo.svg` metadata. A theme project needs those words in
   `.cspell-project-words.txt`. The template dictionary was deliberately left
   untouched rather than preloaded with one theme's vocabulary.

3. **`make subtheme` on the vanilla and cms branches.** Only the localgov
   branch was exercised live. Core's `generate-theme` starterkit invocation is
   still documentation-derived.

## Environment note

`*.ddev.site` does not resolve via DNS on this machine, so `ddev start` needs an
`/etc/hosts` entry and therefore sudo, which a non-interactive session cannot
provide. Reusing a hostname already present in `/etc/hosts` avoids the prompt. A
stale `s10-mod-dev` DDEV registration left by the earlier session, pointing at a
deleted `/tmp` directory, was removed as part of this.
